# ADR-0001：生产环境 MCP 接入以 stdio + token 型为主，OAuth 型走带外授权

- **状态**：Accepted
- **日期**：2026-10-28
- **决策者**：Timothy
- **格式**：MADR（Nygard ADR 的扩展模板：上下文与驱动因素 → 备选方案逐项权衡 → 决策 → 后果）

---

## 上下文

Aster 部署在无头服务器上（腾讯云 Ubuntu，无浏览器、无图形界面），而 MCP server 有两种接入形态：

- **stdio 型**：本地子进程，由 Aster 拉起，凭据以环境变量注入（token）；
- **远程 HTTP 型**：服务商托管，多采用 OAuth 授权码流程——在浏览器中同意、回调打到授权方所在机器的 `127.0.0.1` 监听端口，再以授权码换 token。

OAuth 的回调模型假设「点同意的浏览器」与「等待回调的进程」在同一台机器、同一网络上下文。无头部署不满足这个假设：服务器上没有浏览器；在别处打开授权链接，回调只会落到那台机器的本地端口。

Aster 两类接入均已实现（含 OAuth 的发现、动态客户端注册、PKCE、回调 state/iss 校验、401 后 refresh 恢复），但此前未对真实外部 server 验证过。2026-10-28 以 Notion 托管 MCP 做首次实测：配置、发现、注册、授权同意、回调校验全部走通；在换 token 一步，Notion 端点返回 HTTP 502 与非标准错误码 `refresh_rejected`，三次复现（含一次绕开 Aster 的手工规范请求），判定为对方 Beta 服务故障（证据摘要见附录）。

## 决策驱动因素

1. **部署形态适配**：接入方式必须在无头服务器上自然成立，不靠绕行技巧维持。
2. **接入与排障成本**：单人运维；新接一个 server 应有默认路径，故障要能快速定位到段。
3. **可靠性**：不把生产能力建立在供应商 Beta 服务的可用性之上。
4. **安全**：长期凭据越少越好；不可避免的凭据要纳入既有保管纪律（文件权限、不入仓库、不入日志）。
5. **可验证性**：选定的路线要能在当前环境里真实跑通并留下证据，而不是停留在代码审查层面。

## 备选方案

### 方案 A：远程 OAuth 型为主要路线

- 优点：服务商官方托管、无需本地进程，通常工具最全、更新最及时。
- 缺点：授权流程与无头部署模型错位，每次接入都要靠带外授权或 SSH 隧道绕行（与驱动 1 冲突）；可用性系于供应商成熟度，本次实测即被其 token 服务 502 挡死（与驱动 3 冲突）；失败时对方只给非标准错误码，排障成本高（与驱动 2 冲突）。

### 方案 B：stdio + token 型为唯一路线

- 优点：与无头天然契合——进程由 Aster 拉起、token 走环境变量，整个生命周期无浏览器角色；行为可在本地完整复现与验证（驱动 1、5 最佳）。
- 缺点：要求目标服务有 stdio 发行版且提供 token 申请流程，只有托管版的服务（如现阶段的 Notion 官方 MCP 若无本地版对应物）会被排除在外；token 是长期凭据，保管与轮换责任落在运维一侧（驱动 4 的成本）。

### 方案 C：stdio 优先的混合路线（采纳）

stdio + token 型为默认路线；OAuth 型按需接入，但授权不在服务器上做——在有浏览器的环境完成 `mcp:auth`，把 token 文件部署到服务器数据目录，或经 SSH 隧道（`ssh -L <redirectPort>:127.0.0.1:<redirectPort>`）让回调落回服务器；服务器运行时只依赖已存 token 与 refresh（纯 HTTP）。

- 优点：默认路径满足驱动 1、3、5；同时保留 OAuth 生态的可用性，不因部署形态放弃整类服务。
- 缺点：OAuth 型接入是手工两步（授权、部署），且 token 文件的轮换靠运维纪律，没有自动化兜底；refresh 在无头环境的长期有效性尚未被真实周期检验（驱动 5 的已知缺口）。

### 方案 D：在服务器上补齐浏览器/虚拟显示以完成授权

- 缺点：为「授权时点一次同意」这一个动作引入整套 GUI 依赖，与无头运维相悖，后续维护成本在所有方案中最高。直接否决。

## 决策

**采纳方案 C**：生产环境 MCP 接入以 stdio + token 型为默认；OAuth 型走带外授权（本地授权后部署 token 文件，或 SSH 隧道），服务器不直接跑授权流程。

同时，**Notion 托管 MCP 的接入验证就此搁置**：其阻塞点是对方 token 服务的 502，属方案 A 的固有风险在本案中的具体发作；待对方恢复后可按方案 C 的 OAuth 路径重试，或改验其 stdio 形态。

## 后果

正面：

- 新 server 接入有了默认答案（先看 stdio 版），不再逐案讨论；接入路径与部署形态对齐。
- 搁置决定止住了在供应商故障上的继续投入，实测证据保留完整，随时可按本 ADR 重启。
- 本次未验通的后半程（连接、工具发现、tool_search 注入、真实调用、refresh 长期有效性）被明确标为未验证，不会被误读为已通过。

负面（接受的成本）：

- OAuth 型接入保持手工两步，token 文件成为新的长期秘密资产，须纳入既有凭据纪律（600 权限、不入仓库、不入记忆明文）。
- Notion 托管版的工具能力在对方恢复前用不上；若其 502 长期不恢复，托管生态位将由其他服务填补，届时以新 ADR 修订本决策，而非直接修改本篇。
- 方案 C 的 refresh 缺口意味着：首个真实 refresh 周期（或首次 401 恢复）到来时，需回看本 ADR 核对实际行为，必要时补记。

衍生事项（不在本 ADR 决策范围）：MCP 的配置与排障体验改进（预设目录、引导式添加、健康状态可见）归工具体系（Register）设计处理。

## 附录：2026-10-28 Notion 托管 MCP 实测证据摘要

测试配置存于独立测试工作区（aster-mcp-test），与生产隔离。执行路径逐段：配置读取 ✅、OAuth 发现 ✅、动态客户端注册 ✅（两轮）、浏览器授权同意 ✅（两轮）、回调 state/iss 校验 ✅、授权码换 token ❌（HTTP 502 `refresh_rejected`）、连接与工具发现 ⛔ 未到达。

定位要点：回调因浏览器与执行环境不在同一网络上下文而无法直达（`ERR_CONNECTION_REFUSED`，浏览器原文确认），改由 shell 带外投递、本地服务确认接受，排除重复投递与授权码复用；手工交换请求逐项核对 client_id、PKCE verifier、redirect_uri、resource 无误，结果相同；失败后本地状态文件无 token 落盘。`mcp:check` 对无 token 状态正确报 `MCP_AUTH_REQUIRED`。
