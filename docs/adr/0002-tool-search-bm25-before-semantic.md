# ADR-0002：工具检索先用 BM25 词面检索，语义检索按信号延后

- **状态**：Accepted
- **日期**：2026-10-28
- **决策者**：Timothy

## 上下文

延迟工具池的检索（`tool_search`）需要确定排序方式。现状事实：

- 生产环境当前 0 个 MCP 工具在线，第一批预期一两个 server、几十个工具量级。
- 工具名与参数名高度规范（动词 + 名词，如 `search_pages`、`create_issue`），词面信号强。
- 生产部署在出境受限的无头服务器上，新增外部 API 依赖有通道成本（见 ADR-0001）。
- 工具体系有确定性纪律：同 query 同状态必同结果，搜索结果落盘后重放回放、不重搜。
- 使用场景存在跨语言因素：用户意图是中文，工具描述以英文为主。

## 决策驱动因素

1. 当前规模下的实际命中质量，而非为假想规模付账。
2. 部署依赖最小化：不新增外部服务或本地模型占用。
3. 确定性与可重放：排序结果不得随外部模型版本漂移。
4. 失败可解释、可调：搜不到时要知道补什么，而不是面对黑盒。
5. 单人运维的维护成本。

## 备选方案

### 方案 A：纯 BM25 词面检索（采纳）

字段权重：名字词 > 来源名 > 参数名与描述 > 工具描述。

- 优点：零新依赖（框架已有实现）；结果确定、可复现；失败模式透明，调权重、补同义词即可改进；与现有纪律零冲突。
- 缺点：词面实在对不上时搜不到（有零结果提示兜底）；跨语言靠模型先把意图转成英文关键词，多一层损耗。

### 方案 B：纯语义检索（embedding）

- 优点：跨语言天然匹配；词面不同但语义相近时能召回。
- 缺点：引入新依赖——外部 embedding API 有出境通道问题，本地嵌入模型占用生产机（4 核 / 7.5G）资源；嵌入模型版本变更导致全部向量重算、排序整体漂移，与确定性纪律冲突，除非把模型版本钉进纪元与账本，复杂度显著上升；失败是黑盒，不可调；语义相近但功能不对的工具会被误召回，误加载率可能反升。

### 方案 C：混合检索（BM25 + embedding 双路召回再融合）

- 优点：兼顾词面精确与语义召回。
- 缺点：同时背上方案 B 的全部成本与融合排序的调参成本；在当前工具量级下，收益没有证据支撑。

## 决策

v0.1 采用**方案 A**：BM25 词面检索 + 字段权重。跨语言损耗用提示层折中——模型生成 query 时可中英关键词并置，不动架构。

语义检索**按信号延后**，出现以下任一信号时以新 ADR 重新评估：工具未命中率持续偏高且补同义词无效；工具总量跨过数百；中文描述的工具占到相当比例。

## 后果

- 正面：零新依赖上线；检索行为完全可预测、可归因；与纪元、重放纪律无摩擦。
- 负面（接受的成本）：跨语言检索质量依赖模型生成的 query 质量；词面对不上的少数场景会搜不到，只能由模型换词重试。
- 本决策的适用边界是工具量级（数百以内）与描述语言结构（英文为主），越界即触发重评，不静默沿用。
