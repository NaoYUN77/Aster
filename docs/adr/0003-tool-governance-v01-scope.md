# ADR-0003：工具体系 v0.1 范围——统一治理先行，按瘦身清单分期

- **状态**：Accepted
- **日期**：2026-10-28
- **决策者**：Timothy

## 上下文

Tool Register / Tool Search / Lazy Loading 的完整设计已经定稿（分工、分层、状态机、声明纪元、账本、适配器契约）。但全貌是为「多个 MCP server、数百工具、长对话」设计的，Aster 当前现实是 9 个内置工具、0 个 MCP 工具在线，单人运维。v0.1 需要一个可落地的切分：做哪几块、砍哪几块、按什么顺序。

现状基线（代码已核）：现有注册路径只有重名校验，无 tier/trust/authz 元数据；MCP 连接断开只有日志、没有状态（工具永远显示可用，是已确认的洞）；`tool_search` 的 BM25 与已加载集持久化是框架现成行为；声明纪元与账本字段（加载序号、纪元号）尚不存在。

## 决策驱动因素

1. 每期独立有用、随时可停，不出现「做一半不可用」的中间态。
2. 先补真实踩过的坑：MCP 断线无感、故障排障不可见（ADR-0001 的教训）。
3. 不为未到达的规模预付复杂度；规模到了再按信号补。
4. 有迁移成本的数据结构先行：账本字段越晚补，存量会话迁移越贵。
5. 不动已冻结的语义：MEM 系列的 replay 语义、声明字节稳定性。

## 备选方案

### 方案 A：按设计全貌一次实现

- 缺点：周期长、中间态不可用、为未验证的规模（晋升自动化、版本漂移处理、两段式加载）预付全部复杂度；单人运维下烂尾风险最高。否决。

### 方案 B：只做 Register 元数据化（最小集）

- 优点：最快落地。
- 缺点：元数据化本身不改变任何行为，断线无感这个真实的洞还在；做完仍需再立项补健康接线，等于把同一个区域改两遍。否决。

### 方案 C：治理核心先行 + 明确瘦身清单（采纳）

v0.1 范围（按此顺序分期）：

1. **元数据化 + 账本字段**：注册路径补信封字段（source / tier / trust / replay / authz / schemaHash）与状态查询；已加载集账本补加载序号与纪元号。
2. **健康状态机接线**：MCP 断开/重连经适配器事件驱动 available ⇄ unavailable；搜索投影只含 available；已加载但不可用的工具由执行层拦截报错。声明不随健康翻转变更（纪元纪律）。
3. **手动 pin 晋升**：配置驱动、周期边界生效、A 区预算校验；不做自动晋升候选。
4. **执行复核与 authz 落地**：调用前经 Register 复核存在性、状态、授权；MCP 工具 authz 默认 write，所有者可在配置中逐个覆盖，annotations 不作定级依据。

瘦身与延后清单（明确不做，触发条件见各条）：

- 状态机的 discovered / registered 两态**合并为一态**（全设计中收益最薄的一截，异步增量注册的实际复杂度未出现前不分开）；
- schemaHash 只记录、**不处理漂移**（等第一次真实 MCP 工具升级事件再补退休/换绑）；
- **不做插件加载器**（信封与适配器契约预留 plugin 字段即可）；
- **不做两段式加载**，维持搜索即加载（误加载率持续超三成再议）；
- **不做语义检索**（ADR-0002）；
- 健康侧**先接 onClose 事件，ping 探活与运行期对账延后**（等出现静默假死案例再补）。

## 决策

采用**方案 C**。v0.1 = 上述四期范围 + 瘦身清单，实现拆为 TOOL-01～04 四个 issue 分期推进，每期合并后系统保持完整可用。

## 后果

- 正面：每一期都对应一个真实问题或一笔已知的迁移债；v0.1 落地后，MCP 断线可感、工具状态可查、授权有复核、账本可支撑后续纪元机制。
- 负面（接受的成本）：实现与设计全貌存在已知偏差（合并态、漂移未处理、无探活），后续补齐须走新 issue / 新 ADR，不在本期顺手扩张；账本字段先行有一笔前置成本，但小于日后迁移存量会话的成本。
- 与 ADR-0001 的关系：接入策略不变；本 ADR 只裁工具体系的实现范围。
