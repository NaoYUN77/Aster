## 3. 阶段 A：建立可复现基线

### 执行动作

1. 检查 Node/npm 版本、依赖安装状态及锁文件一致性；要求以版本文件和依赖清单为准。仅在依赖缺失或安装不一致时使用 `npm ci`。
2. 依次运行当前 `package.json` 中的类型检查、全量离线测试及构建。当前入口为：

   ```sh
   npm run check
   npm test
   npm run build
   ```

3. 如测试失败或挂起，先保留失败用例、错误和环境信息，再定位原因。隔离运行相关测试文件；每个异步验证具有超时与资源清理。区分环境不满足、产品缺陷和测试缺陷。
4. 新建 `docs/mvp-verification.md`，记录本次环境、基线命令及结果。该文件承载后续验收记录，避免把任务进度写回 `CLAUDE.md`。

### 完成标准

三个检查全部通过，测试无失败、取消或意外跳过。初始应能发现现有 13 项用例；新增测试后记录实际数量。如环境使检查无法运行，标记“阻塞”并说明恢复条件，不能标记本阶段完成。

## 4. 阶段 B：核实契约并修复具体差异

### B1. 文档与实现对齐

- `src/agent.ts` 已设置 `toolExecution: "sequential"`。验证对应行为后，将契约文档中仍表示“拟配置”的表述更新为当前事实。
- 核实 `src/inbox.ts` 的 `prune()`：当前子查询取全部请求中最新 100 条，再删除不在其中的已发送记录；README 和注释描述的是保留最近 100 条已完成请求。
- 默认按现有文档意图保留最近 100 条已发送请求，同时保留所有未完成请求。以混合状态数据验证差异后做最小修复；核对关联投递／诊断记录的清理行为，保持事务和去重语义。

完成标准：保留策略有一个明确含义，测试使用超过保留阈值且混有未完成请求的数据证明它，代码与文档一致。

### B2. 工具边界与资源限制

- 检查实际注册工具的参数 schema、未知字段策略、执行校验路径、结果和重放声明。确认非法参数经 Harness 路径不会进入执行函数；现有测试覆盖的情况直接复用。
- 核查底座文件工具与 bash 的输出上限、超时、取消传播及截断提示，记录已安装实现的证据。应用提示词要求“限制输出和时间”不能单独作为强制限制的证明。
- 核查输入、最终回复、待处理请求和持久化数据增长边界。轮询一次最多 10 条不自动等于整个积压队列有上限。区分 Telegram 远端积压、本地收件积压及失败投递记录。
- 对明确缺口，优先使用底座已有配置。确需应用补充限制时，在所属边界实现，记录选值与超限行为，并测试真实的超限场景。
- 如底座必然截断工具输出，确保结果能明确指出截断，并提供分页、缩小查询或文件引用等后续路径；用户输入不能静默丢弃。

完成标准：`docs/mvp-verification.md` 中列出各资源的实际限制、执行位置和超限行为；尚未解决的硬性边界缺口作为发布阻塞项保留。

## 5. 阶段 C：补齐失败与恢复证据

先将以下场景映射到现有测试，只补缺失或不足的证据。使用真实 pi durable 和 SQLite、离线模型替身，以及可控的 Telegram API 替身。测试目录与日常数据目录隔离。

| 场景 | 必须证明的结果 |
| --- | --- |
| 接收事务与重复请求 | 同一请求重复接收不重复创建业务执行；同 ID 不同内容被拒绝，消费位置不错误前进；同内容不同 ID 是独立请求 |
| 已提交但应用未记录结果 | 使用原 requestId 找回原执行；已完成请求不新增模型或工具调用 |
| 回复已保存、尚未投递 | 重启使用已存回复继续投递，不重跑 agent |
| 多段回复部分成功 | 已确认段保持原样，只处理允许继续的未确认段 |
| 发送明确失败与结果未知 | Telegram 明确拒绝和连接中断等不确定结果分开记录；未知结果不自动重发 |
| 人工核查补发 | `retry`／`sent` 只调整指定投递段，后续发送复用已保存文本，不执行业务工具 |
| 工具失败后修正 | 非法参数或业务错误可被模型处理，不自动将整个用户请求判失败 |
| 工具中断重放 | 可安全重放的测试工具按底座规则恢复；不安全工具不能因重启重复产生副作用；底座具体终态和错误均有证据 |
| 实际执行取消 | 取消信号到达实际工具 I/O；对长时间命令及其普通子进程，取消后不再继续预设的延迟写入，资源最终释放 |
| 正常关闭与进程崩溃 | 正常关闭保留未完成请求；强制结束后重开数据库仍能按契约恢复，不将执行恢复和投递恢复混为一体 |

实施要求：

- 工具重放用临时文件或测试计数器模拟副作用。仅验证模型取消不足以证明 bash 或外部工具已经停止。
- 对进程崩溃窗口，使用独立子进程和明确同步点；父进程在目标状态持久化后结束子进程，再启动新进程检查结果。避免依赖固定睡眠猜测时序。
- 底座恢复状态和工具调用关联直接读取底座提供的记录，不额外维护等价状态机。
- Windows 无法代表 Linux 子进程／信号行为的项目，单独列入阶段 F。标明本地覆盖边界，不能通过跳过测试宣称目标环境通过。

完成标准：表内每项都有测试或可复现的验证记录；已覆盖项引用现有用例即可。所有发现的本地产品缺陷修复，相关测试及全量检查通过。目标环境专属事项明确留待阶段 F。

## 6. 阶段 D：交付可运行的本地版本

1. 同步实际发生变化的配置、运行方法和契约。README 保留运行说明，设计文档保留设计，验收记录保留证据。
2. 核实缺少必要配置时能给出清晰错误；无凭据检查采用显式测试环境，不连接生产服务。
3. 运行类型检查、全量测试和生产构建。记录最终命令、退出结果、测试数量及本次变更文件；若上一轮已在最终代码上完成这些检查，可直接引用结果。
4. 输出本地交接摘要：已完成能力、已修复问题、剩余联调与部署项，以及启动入口。

完成标准：阶段 A—C 的本地事项全部闭合，构建产物与源码一致，文档能指导配置和运行。此时状态为“本地验证完成，真实联调／部署待验收”，不等同于 MVP 已上线。

## 7. 阶段 E：真实 Telegram 与模型联调

执行条件：已有可用测试 bot、owner ID、受支持提供商的模型凭据，以及用户对该测试环境的联调授权。使用隔离的数据目录和测试内容；缺少条件时明确列出所需配置项，完成其余工作后交接。

按 `docs/mvp.md` 七条验收逐项记录，并覆盖：

1. 授权用户发送文本，能收到有效最终回复；连续请求共享上下文，多条消息按顺序处理。
2. 真实模型调用 `current_time`，最终答复与工具结果一致。非法参数拒绝继续使用离线可控测试作为确定性证据。
3. 明确要求记住一个无敏感信息的事实，经记忆工具写入 working 状态或每日归档，重启后仍能读取；普通聊天不自动追加记忆。不要再把 `workspace/MEMORY.md` 当作当前通道，见 [ADR-0004](adr/0004-retire-workspace-memory-md.md)。
4. 非 owner／非私聊输入不触发模型或工具。无法获得第二个账号时保留离线边界测试，并将真实验证标为未覆盖。
5. 长回复分段完整，失败诊断可区分模型、工具与 Telegram 出口；完整工具记录仍保存在底座中。
6. 重启后能继续处理待完成请求；对失败／未知投递，停应用、核对实际聊天记录，再按 [投递核查与补发](deliveries.md) 操作。

完成标准：真实验收项记录时间、请求标识、脱敏观察结果和证据。不可稳定制造的网络未知窗口由阶段 C 的故障注入证明，并注明与真实联调的区别。

## 8. 阶段 F：4 核／4 GB Linux 部署验收

执行条件：目标主机及部署授权可用；部署步骤沿用 README 和现有 service 示例。

1. 核对 Node 版本、服务用户、目录权限和环境配置，验证 `flock` 的单实例行为。
2. 验证构建产物、应用代码和持久化目录分离；重新部署后记忆、会话、收件与投递记录仍存在。
3. 验证 SIGTERM、systemd 停止时间限制与底座关闭行为的配合，以及强制终止后恢复。复测 Linux 下 bash 及普通子进程的取消行为。
4. 记录空闲、典型请求、工具执行和重启期间的服务内存峰值、进程／子进程数量、主机可用内存及磁盘增长。确认服务和工具子进程受既有资源限制约束，无 OOM 或失控积压。
5. 验证日志能区分执行与投递问题，凭据不出现在常规日志中。
6. 验证备份与还原：先停止服务并确认数据库连接关闭，再备份整个持久化数据目录；恢复到独立目录验证记忆、会话和投递状态。若使用在线备份，必须采用 SQLite 支持的一致性备份方式。
7. 按实际使用流程完成一次投递核查演练，保留逐段记录；未知投递在核实后再决定补发。

完成标准：目标环境的测量和恢复结果可复现，MVP 七条验收已满足，未覆盖窗口与使用限制有明确记录。没有真实主机验证时，交付状态保持“部署待验收”。
